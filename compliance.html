DATA PRACTICES FOR SCHOOL REVIEW

Useful practice.
Clear privacy boundaries.

Cole Learning Labs provides free browser-based technology activities for grades K–12. This statement explains the public labs, optional online services and completion-code limits so district technology teams and Data Protection Officers can review the actual workflow.

Operator: Alan “Al” Cole · Updated November 11, 2026

Review status

Public labs require no learner account. Aggregate activity counts, optional lab telemetry and signed completion codes are three separate features, and all three are off in this release. Aggregate counts have the owner's source review and are held off by hosting configuration; telemetry and completion codes still await review and configuration. Online requester replies are not offered in the current public build. This page does not establish school approval, a completed legal assessment or vendor certification. Districts decide whether a particular use requires an agreement or other safeguards.

Real Linux machines process work remotely

Choosing Start machine opens a hosted Linux machine. The website sends the lab ID, display dimensions, session messages, keyboard and pointer input, and work-check requests. The remote machine processes its files and commands and returns screen or terminal output. The controller reads the lab files and recent command history needed to check progress. Anything typed into that machine or saved in its files leaves the browser, including personal information entered by mistake.

Cloudflare relays the connection, DigitalOcean hosts the controller, and the cloud backend uses Docker Cloud Sandboxes for learner machines. Providers process connection and operational metadata under their own applicable terms. The remote screen is the lab machine’s display; the site does not capture the learner’s own screen, other tabs, camera or microphone. Use fictional files and details only; never enter student records, names, contact details, passwords, private keys or confidential school information. Starting a machine is a product action, not parental consent or district authorization.

The service requests machine deletion on Stop, disconnect or session timeout. Network failures, controller restarts or provider errors can delay or prevent cleanup. Provider logs, recovery copies and retention require separate verification; immediate or complete erasure is not guaranteed. Clearing browser work does not erase provider copies. Before school use, review the selected features, required authority and agreements, provider terms, rights procedures and tested deletion with the district. See the School IT review.

Three separate optional services

Aggregate activity counts, optional lab telemetry and signed completion codes have separate purposes, switches and reviews. Turning one on does not turn on another. Telemetry and completion codes share the address /api/telemetry, but a code request writes no telemetry unless the learner has separately chosen to share activity totals for that visit, and no learner has to share telemetry to get a report or a code. “When on” describes the prepared design, not something that happens in this release.

What a completion code can establish

A valid signature means the code matches fields issued using the server's signing key. The key stays on the server and is never included in browser JavaScript. A signature can detect a changed lab, score, duration or date after issuance.

Public simulations run on a learner-controlled browser. A caller can modify local state or submit inaccurate results before signing. Codes therefore do not prove mastery, independent work, identity or attendance. A copied valid code remains valid; the teacher verifier can flag repeated codes within the pasted batch, but it cannot identify who completed the work or detect every reuse. Use the report, a demonstration or a discussion alongside any code.

Paste codes only into the teacher code verifier, without names, email addresses or roster columns. When the verifier page opens, it makes one availability request (GET /api/verify) that carries no codes, and it reports whether verification is available before asking for any. The service is off in this release, so the page reports that verification is not enabled. Verification sends the pasted codes to this website only if the service is enabled. Codes contain performance-related fields and can become identifiable when linked to school records. Keep the identity mapping and grading decisions in the district's approved system. The disabled service must never display an unverified code as verified.

New York Education Law §2-d and Part 121

Applicability depends on the information and actual school/vendor arrangement. NYSED's guidance places the assessment of whether covered personally identifiable information is provided with the school district. A public URL, no-login design or label such as “anonymous” does not decide that question. When covered data will be received, applicable agreements and protections must be completed before collection. See NYSED's DPO and vendor guidance and Education Law §2-d.

FERPA and COPPA considerations

FERPA protects personally identifiable information from education records. Removing a name does not necessarily remove indirect identifiers. Schools should review the full data flow, including reports, performance fields and provider metadata, before using an online service with records. See the U.S. Department of Education's online educational services guidance.

COPPA can apply to online collection of personal information from children under 13, including certain persistent identifiers. It is not limited to names or email addresses. Required notices, authority, security and deletion procedures must be assessed for the actual service. This page does not claim a blanket internal-operations exception. See the FTC's COPPA compliance guidance. New York’s Child Data Protection Act also covers personal data reasonably linkable to a person or device. Necessary processing for a requested service and optional secondary uses need separate analysis; a learner checkbox is not a substitute for required consent, school authority or binding processor terms. Review the permitted-processing rules and processor obligations; see the Attorney General's implementation guidance.

Optional cloud replies and provider processing

Online requester replies are not offered in the current public build. Every reply comes from the built-in character, and the page sends no reply request. The rest of this paragraph describes the reviewed design, which applies only if a later approved release offers the option. In that design, cloud requester replies start off on each fresh page. Choosing the visible AI control checks availability. A later eligible question sends only a fictional lab ID and predefined topic ID through the website to its private Cloudflare AI service. Typed questions, reports, notes, conversation history and equipment state stay local in that flow. Built-in replies remain available when the service is off or unavailable. Read the AI use and limits notice and full privacy information.

Optional online requests may use Cloudflare Turnstile. It processes connection and browser security signals, including IP address, TLS fingerprint, user-agent and site origin, for bot detection and its improvement. It does not establish a learner's identity or achievement. Cloudflare's Turnstile Privacy Addendum and privacy policy describe provider processing. Current provider settings, logs, recovery copies and retention require their own review.

District network and retention review

Use HTTPS on www.colelearninglabs.com; the apex colelearninglabs.com redirects there. Optional Turnstile requests use challenges.cloudflare.com; no published page loads it in this release. The server-side reply gateway at /api/requester remains enabled in the production hosting configuration; the published page never calls it. Public labs do not require broad wildcard allowances for every Cloudflare or GitHub hostname. HTTPS, HSTS and a Content Security Policy reduce risks; they do not guarantee that data cannot leave a device. Test the actual managed browser, network and selected features. The School IT review includes device and filtering information.

Independent browser work can be cleared with the site's local-work controls. Downloaded reports, clipboard contents, backups and school submissions require separate deletion. There is no approved retention schedule for the new telemetry service because it is not active. Before activation, document and test purpose limits, necessary retention, scheduled deletion, provider recovery periods, access, incident handling and rights requests. Disabling future collection does not erase earlier copies.
