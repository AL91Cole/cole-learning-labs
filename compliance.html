DATA PRACTICES FOR SCHOOL REVIEW

Useful practice.
Clear privacy boundaries.

Cole Learning Labs provides free browser-based technology activities for grades K–12. This statement explains the public labs, optional online services and completion-code limits so district technology teams and Data Protection Officers can review the actual workflow.

Operator: Alan Cole · Updated November 4, 2026

Review status

Public labs require no learner account. Online receipt issuance and lab telemetry remain disabled in this release pending review and configuration. This page does not establish school approval, a completed legal assessment or vendor certification. Districts decide whether a particular use requires an agreement or other safeguards.

Data practices at a glance

FeatureWhat happens
Public labs and accountsNo student registration, email address, roster or school sign-in is required. Fictional lab work runs in the browser. Connected classroom collection remains locked for a separate privacy review.
Saving and reportsWork starts in page memory. Device saving requires an explicit choice. A learner can review and download or copy a report, then submit it through a district-approved system. Notes or reports can contain personal information if a learner enters it; use fictional information.
School systemsThe public workflow requests no Google Classroom OAuth access, roster import or grade synchronization. School systems receive the files or codes that a learner or teacher chooses to submit there.
Local active timerThe timer estimates active time while the lab is visible, counting the first minute after opening and up to 60 seconds after each interaction. It pauses after 60 seconds without interaction and when the lab is hidden. It does not record typed keys, pointer paths, other-tab contents or screenshots. Time is a browser estimate, not attendance evidence.
Optional signed codesIf enabled after review, a request would send a fixed activity ID, browser-reported score and active seconds to the website, after a Cloudflare security check. A server signature protects the returned fields against later edits. It does not independently validate the reported score or time. No student name is part of the code.
Optional lab telemetryCollection is disabled. Any later activation must disclose the approved fields, aggregate storage, retention, provider processing and controls before sending events. A date-only field does not make transport anonymous or eliminate possible correlation. Each participating lab makes one availability request (GET /api/telemetry) when it opens, to learn whether these optional services are on. That request carries no activity data, cookie or referrer, and the application stores nothing from it. Cloudflare still receives normal connection information.
Hosting and securityCloudflare receives normal connection and security information when delivering the site. This can include IP address, browser and requested path. The absence of those fields from an application table does not mean the provider receives or retains nothing.
Advertising and trackingThe public lab application includes no advertising SDK, behavioral advertising pixel, remote font or embedded social feed. Cloudflare delivery and optional security services have their own processing described below. School-managed browsers and networks have separate practices.

What a completion code can establish

A valid signature means the code matches fields issued using the server's signing key. The key stays on the server and is never included in browser JavaScript. A signature can detect a changed lab, score, duration or date after issuance.

Public simulations run on a learner-controlled browser. A caller can modify local state or submit inaccurate results before signing. Codes therefore do not prove mastery, independent work, identity or attendance. A copied valid code remains valid; the teacher verifier can flag repeated codes within the pasted batch, but it cannot identify who completed the work or detect every reuse. Use the report, a demonstration or a discussion alongside any code.

Paste codes only into the teacher code verifier, without names, email addresses or roster columns. Verification sends the pasted codes to this website if the service is enabled. Codes contain performance-related fields and can become identifiable when linked to school records. Keep the identity mapping and grading decisions in the district's approved system. The disabled service must never display an unverified code as verified.

New York Education Law §2-d and Part 121

Applicability depends on the information and actual school/vendor arrangement. NYSED's guidance places the assessment of whether covered personally identifiable information is provided with the school district. A public URL, no-login design or label such as “anonymous” does not decide that question. When covered data will be received, applicable agreements and protections must be completed before collection. See NYSED's DPO and vendor guidance and Education Law §2-d.

FERPA and COPPA considerations

FERPA protects personally identifiable information from education records. Removing a name does not necessarily remove indirect identifiers. Schools should review the full data flow, including reports, performance fields and provider metadata, before using an online service with records. See the U.S. Department of Education's online educational services guidance.

COPPA can apply to online collection of personal information from children under 13, including certain persistent identifiers. It is not limited to names or email addresses. Required notices, authority, security and deletion procedures must be assessed for the actual service. This page does not claim a blanket internal-operations exception. See the FTC's COPPA compliance guidance. New York's additional child-data requirements also need review; see the Attorney General's implementation guidance.

Optional cloud replies and provider processing

Cloud requester replies start off on each fresh page. Choosing the visible AI control checks availability. A later eligible question sends only a fictional lab ID and predefined topic ID through the website to its private Cloudflare AI service. Typed questions, reports, notes, conversation history and equipment state stay local in that flow. Built-in replies remain available when the service is off or unavailable. Read the AI use and limits notice and full privacy information.

Optional online requests may use Cloudflare Turnstile. It processes connection and browser security signals, including IP address, TLS fingerprint, user-agent and site origin, for bot detection and its improvement. It does not establish a learner's identity or achievement. Cloudflare's Turnstile Privacy Addendum and privacy policy describe provider processing. Current provider settings, logs, recovery copies and retention require their own review.

District network and retention review

Use HTTPS on www.colelearninglabs.com; the apex colelearninglabs.com redirects there. Optional Turnstile requests use challenges.cloudflare.com. Public labs do not require broad wildcard allowances for every Cloudflare or GitHub hostname. HTTPS, HSTS and a Content Security Policy reduce risks; they do not guarantee that data cannot leave a device. Test the actual managed browser, network and selected features. The School IT review includes device and filtering information.

Independent browser work can be cleared with the site's local-work controls. Downloaded reports, clipboard contents, backups and school submissions require separate deletion. There is no approved retention schedule for the new telemetry service because it is not active. Before activation, document and test purpose limits, necessary retention, scheduled deletion, provider recovery periods, access, incident handling and rights requests. Disabling future collection does not erase earlier copies.
